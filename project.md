# MarketTrace — project blueprint

**Status (2026-11-06):** This is the original phase blueprint. A synthetic offline candidate now runs and has been independently reviewed in `CODEX_PHASE9_AUDIT.md`. Cloud Snowflake, live capture, persisted revisions, and credible performance benchmarks are still pending. Acceptance gates below describe goals, not a retrospective pass report.

## The problem

Market data is used to calculate prices and risk measures. A duplicated, invalid, late, or missing order-book update can make those calculations misleading. Catching an error is only the first step: an engineer also needs to know which results used the bad or incomplete evidence, whether a current book can be trusted, and what can actually be repaired.

MarketTrace asks one concrete question: **Can we replay a BTC-USD order-book incident, explain exactly which downstream calculations are affected, and prove which results recover?**

A currency-conversion page would not answer it. This project tests event processing, reproducible recovery, data provenance, and targeted recomputation. It does **not** place orders, predict returns, implement an FPGA, or claim to be a low-latency trading system. Existing Snowflake quality and lineage features are relevant comparisons; the aim is to demonstrate a specific cross-boundary incident workflow, not to claim those products lack lineage.

## What the finished project should look like

From a fresh checkout, a reviewer runs a documented offline demo without credentials. It replays a small synthetic BTC-USD book, injects a fault, records the C++ engine's decision, shows the book's validity and affected metric windows, applies an authoritative resynchronization snapshot or a separately labeled fixture correction, and compares resulting revisions with an independent Python reference. Two identical replays produce the same canonical outputs. The dashboard has three focused views: run overview, incident evidence, and recovery comparison.

When Snowflake credentials and a finite trial budget are available, the same bounded run uploads preserved evidence to Snowflake and calculates historical midpoint, spread, and one precisely defined rolling volatility measure. SQL results are compared with the independent reference. A local DepGraph extension explains the dependency path and the exact windows to recompute. The README includes a real case study, actual measured results, limitations, commands, and cost. An optional live adapter captures a short public feed session only after the offline path works; it never turns a missing live update into invented history.

The reviewer should be able to click an incident and answer: **What arrived? What rule failed? What state was trusted? Which calculation windows changed? What evidence justified recovery? Which historical gaps remain unresolved?**

## Fixed v1 scope and boundaries

| Part | Responsibility | Output used by the next part |
| --- | --- | --- |
| Synthetic fixture and independent reference | Define known truth, input order, clocks, and injected faults | Versioned event files, expected states/results, hidden evaluator fault labels |
| C++20 engine | Normalize deliveries, maintain book, validate, log decisions, replay and resynchronize | Immutable raw deliveries, decisions, checkpoints, incidents |
| Snowflake | Bounded batch storage and historical SQL calculations | Versioned analytical results linked to evidence |
| Adapted DepGraph | Explicit typed dependencies and affected-window/recompute planning | Impact explanations and result revision plan |
| Local dashboard | Explain run, incident, impact, and recovery | Human-reviewable case study and demo |

The C++ engine never waits for Snowflake to decide whether to accept an update. A local orchestrator sequences offline replay, optional upload, analysis, impact computation, and display. The Python reference is an independent verifier, not a second production engine. The original DepGraph repository infers candidate edges between tool fields; it does **not** already provide market-data runtime, SQL lineage, or time-window impact analysis. Phase 0 determines how to preserve its history and attribute adapted logic.

Earlier INR/USD conversion, ECB/OANDA quote, portfolio analysis, and FPGA ideas were alternative directions. They are outside v1. Start with one instrument, one synthetic snapshot, 100 deterministic updates, one fault, one impacted rolling window, a valid resync, and reference comparison. Add volume or a live feed only after this story works.

## Shared contracts to freeze before implementation

1. **Event envelope:** `run_id`, unique `delivery_id` for every arrival, `source`, `source_session`, `instrument`, `message_kind`, arrival/replay times, raw payload/hash, and optional provider event ID/sequence/time only if actually supplied. Snapshot/update payloads have side, integer price ticks, and integer size units as appropriate. A duplicate still gets a distinct local delivery ID. Define the ordering policy, tick and size scales, rounding, snapshot/update semantics, and explicit timer events. A local counter is never called a provider sequence.
2. **Evidence and identity:** preserve *all* raw arrivals, including rejected ones. A processing decision points to its delivery; a checkpoint/incident points to decisions; a result points to its exact inputs, time window, calculation version, and run. The immutable run manifest records input hash, seed, fault-manifest hash, code revision, config hash, clock policy, calculation version, and upload status. Repaired results are new revisions, never silent overwrites.
3. **Quality states:** distinguish book validity, incident outcome, and analytical-result status. Results may be `VALID`, `STALE`, `INCOMPLETE`, `BLOCKED`, or `RECOMPUTING`. An incident may be open, resumed with an unresolved gap, recovered with authoritative evidence, or unresolved. A current book resynchronized by a fresh snapshot may be valid while older windows remain incomplete.
4. **Calculations:** for a valid nonempty book, best bid `b`, best ask `a`, midpoint `m = (a+b)/2`, spread `s = a-b`, and optional basis-point spread `10000*s/m` if `m>0`. Reject nonpositive prices and negative sizes; document zero-size deletion, empty/crossed-book handling, and source-specific exceptions. In the controlled fixture, use **11 consecutive valid midpoint observations at declared one-second sample times** to form 10 log returns `r_i = ln(m_i/m_(i-1))`. Report their sample standard deviation `sqrt(sum((r_i - mean(r))^2)/9)`, without annualization. A missing required sample blocks that window; never silently forward-fill. Fix precision and tolerances before looking at results. Live irregular updates need a separately specified resampling/completeness rule or no live volatility display.
5. **Repair limits:** a fresh authoritative snapshot can restore the book *from that point forward*. It cannot reveal a missing earlier event. Historical windows can become valid only if their required evidence is independently recovered or supplied as an explicitly labeled synthetic fixture correction; otherwise retain `INCOMPLETE`. Never make a live gap disappear merely because later prices look plausible.

There are three distinct datasets: a small committed development fixture, a frozen held-out set with different scenario families/seeds, and an optional separately labeled bounded live capture. This is software validation, not ML training. Keep the holdout out of detector tuning. A source without a reliable sequence may not make every dropped update observable; evaluate only faults for which the engine has evidence.

## Phase-to-phase interface and end-to-end proof

The minimum vertical slice is: **fixture → raw deliveries → C++ decisions and book state → bounded warehouse results → DepGraph impact/revision plan → dashboard explanation → independent comparison**. Each arrow has a stored identifier/hash, a small fixture test, and a documented command. If an output changes format, update its consumer and the contract tests in the same phase. Avoid a dashboard that calculates its own midpoint or silently chooses its own quality rules.

The showcase incident has two clearly separated endings. First, omit an observable synthetic update so the engine marks uncertainty and downstream windows containing missing evidence are incomplete. An authoritative later snapshot restores a trustworthy *current* book, while the historical gap stays visible. Then, in a separate controlled fixture branch, supply the deliberately withheld authoritative event, recompute the affected windows, write new result revisions, and compare them with the clean reference. Unaffected results must retain their prior revisions. This distinction is the project's main proof of honest recovery.

## Delivery, budget, and honest claims

Run the engine, fixtures, orchestrator, DepGraph module and dashboard locally. Use an X-Small Snowflake warehouse with auto-suspend, a warehouse resource monitor, on-demand batch loads and finite experiments. Record actual credits and remaining trial balance if accessible; a warehouse monitor is not a universal cap on serverless services. Do not start an account, enter payment details, or expose credentials in Git, logs, screenshots, or chat. Offline CI must require no network, account or secrets; optional integration tests are explicitly budgeted.

The README is the public explanation: problem and user story, what was built, architecture and data provenance, one-command offline demo, Snowflake setup/teardown, a before/after case study, real measurements, limits, and what was adapted from DepGraph. GitHub publication is the final reviewed step, not evidence that the project was already completed. The portfolio claim is a demonstrated, reproducible reliability workflow; hiring attention, novel research, and performance superiority are not promised.
